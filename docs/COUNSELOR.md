# Heard — AI support

The main frontend is now a conversation-first AI support app. It listens to ordinary concerns, responds using conversation context, and supports text input in both text and live voice sessions. It does not perform inventory operations, book appointments, diagnose, or provide therapy.

## Start on Windows

From the repository root, with the existing Python and frontend dependencies installed:

```powershell
.\start-counselor.ps1 -Restart
```

Open **http://localhost:5173**. Choose **Start talking** and allow microphone access, or **I prefer to type**. In a voice session, the message field remains available. **Pause voice** pauses audio and microphone input; typed conversation still works. **Resume voice** resumes the microphone. **End conversation** clears the transcript from app memory.

Provider configuration is read from the ignored local `app/.env`. `COUNSELOR_PROVIDER=vertex` uses paid Gemini through Google Cloud; `COUNSELOR_PROVIDER=groq` selects Groq explicitly. LiveKit transports voice, Deepgram transcribes, and Rime speaks. `WORKER_SECRET` authenticates the internal bridge. The privacy dialog identifies the active text provider. Provider failures are surfaced without silently routing a conversation elsewhere.

For Vertex, use `GOOGLE_CREDENTIALS_BASE64` for service account JSON encoded as base64. The server decodes it in memory and renews access tokens through Google's authentication library; it does not create a decoded key file. Base64 is encoding, not encryption. `GOOGLE_CLOUD_PROJECT` can be omitted when the service account supplies it. Application Default Credentials are also supported; specify a project for that path. Never put credentials in `VITE_` variables or `.env.example`.

Text uses `VERTEX_MODEL=gemini-3.1-pro-preview` with `VERTEX_THINKING_LEVEL=MEDIUM`. Voice uses `VERTEX_VOICE_MODEL=gemini-3-flash-preview` with `VERTEX_VOICE_THINKING_LEVEL=MINIMAL` on the same Google provider, with the same safety and conversation context. Both profiles use `GOOGLE_CLOUD_LOCATION=global` by default. The voice profile is separately configurable. Google's [Gemini 3 Flash documentation](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-flash) describes the available thinking levels. The integration uses the [Gemini streaming API](https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/models/inference).

On September 10, a single identical synthetic conversation took 8.58 seconds on the original Pro/MEDIUM setting, 7.23 seconds on Pro/LOW, 3.72 seconds on Flash/LOW, and 3.08 seconds on Flash/MINIMAL. These are development observations, not latency guarantees or end-to-end microphone measurements. Three further voice safety/identity cases completed in 1.83–3.55 seconds and were manually inspected for the stated scenario criteria. Reports are in the ignored `app/.cache/latency-*.json` files. The evaluator accepts `--mode live` to exercise the voice profile.

Rime Coda now uses its official `hesse` voice, described by [Rime's voice catalog guide](https://www.rime.ai/resources/how-we-chose-the-voices-of-coda) as relaxed and easygoing. Spoken wording uses short sentences, contractions, and ordinary punctuation following [Rime's prompting guidance](https://docs.rime.ai/docs/prompting). No SSML, fake laughter, or performance tags are added. A synthetic Hesse check produced initial audio in 1.719 seconds with a cold connection and 0.375 seconds with a reused connection; perceived naturalness still needs listening in the actual device/environment.

The API entry point is `counselor.app:app` under `app/backend`; the worker is `counselor.worker`. Both use the `heard` agent and room prefix. The React entry point is `app/web/src/App.tsx`. Provider configuration, dispatch, and voice request models live in the counselor package. See the root [README](../README.md) for installation, checks, and the source layout.

## Conversation and data behavior

The app sends eligible conversation history to the selected provider. Interrupted voice responses remain visible as interrupted in the transcript and are excluded from completed assistant history. Up to three interrupted drafts/replies are carried separately as bounded, quoted background alongside the original user input and newest correction. Generated-but-unspoken text is labeled explicitly; synchronized playback receipts refine estimated spoken fragments without treating them as facts the user heard or agreed with. The latest user words take priority. Uncertain transcriptions prompt clarification instead of invented meanings or emotions. This temporary context is cleared after a successful replacement reply or session end. Streaming text is shown as a draft; it becomes a completed message only after the provider finishes successfully. Drafts are cleared on interruption, failure, and session end. Speech starts after a complete reply is available. Late results and retired worker callbacks cannot replace a newer turn.

Session tokens are stored in the current browser tab. Transcripts live only in process memory, bounded to 200 messages. The model can receive all eligible messages within a conservative 64,000-byte history budget, keeping complete recent messages when older history must be omitted. A user-written note of up to 600 characters stays available independently of this history window. It is user-supplied context, not an inferred diagnosis or a system instruction. There is no memory across sessions. Ending a session clears the transcript and note, restarting the API clears all sessions, and sessions inactive for one hour expire. Audio is not recorded by this app. The providers have their own data handling policies; the UI explains this before users share sensitive information.

**Just listen** emphasizes reflection without unsolicited advice. **Talk it through** follows a concern without repeatedly asking answered questions. **One small step** helps with one manageable action. The user's latest explicit request takes precedence over their selected style. Changes apply to the next reply; a reply still being generated is cancelled and regenerated with the updated preferences. These are model instructions, not guarantees of conversational quality.

Voice detection allows 0.8 seconds of silence to accommodate pauses, and requires 0.15 seconds of speech before detecting an onset. These are starting settings, not measured acoustic performance. The current speech-recognition path is English; text can follow the user's language. Quiet view measures microphone/output frequency data locally to animate the orb. It does not infer emotion or record that audio. Processing uses a 10-second breathing cycle (six cycles per minute); pause and reduced-motion preferences keep it still. Live captions use the SDK's synchronized `lk.transcription` streams, including corrected user transcripts. Secondary conversation preferences stay collapsed in quiet view.

The session payload includes `ui.status` (`LISTENING`, `PROCESSING`, `SPEAKING`, or `PAUSED`), `ui.phase` (including `PROCESSING_FUSED_CONTEXT`), a monotonic `ui.interruption_id`, `ui.overlay`, `ui.crisis_id`, and an optional processing acknowledgement. The browser also uses actual audio/voice events and local microphone permissions: a muted or disconnected microphone never appears to be capturing speech. On VAD onset the worker clears its public audio-output buffer and cancels current/queued speech, then cancels API generation through the ordered control bridge. Reliable `heard.voice` packets emit `USER_INTERRUPTED` plus `LISTENING` and an explicit `clear_audio` command; subsequent packets include `PROCESSING_FUSED_CONTEXT` and `SPEAKING`. The browser pauses and detaches the old live media stream, resets the visualizer/captions, and restores the live stream only for fresh speech. Worker epochs and sequence numbers fence stale packets; delayed SDK state attributes cannot reopen interrupted playback. This app uses WebRTC media rather than browser-managed TTS WebSocket chunks; SDK cancellation clears the Rime synthesis/LiveKit audio queues. The 150 ms VAD onset and 100 ms interruption settings target quick words such as 'wait' or 'no'; total acoustic-to-browser delay also includes buffering and network transit, so a sub-200 ms end-to-end guarantee is not claimed.

Long disclosures may receive one short spoken acknowledgement after 1.2 seconds of processing if no text has started arriving; it is interruptible, excluded from conversation history, and cancelled as soon as the full reply is ready. Greetings and microphone checks have immediate grounded replies. Vertex voice requests with no first text after `VERTEX_VOICE_RETRY_DELAY` (default 3.5 seconds) start at most one parallel attempt using the same provider/model/context. The first stream to produce text wins; the other is cancelled. No retry starts after text begins, and an interruption cancels both attempts. This can incur a second paid request on stalled turns; it does not guarantee a latency ceiling. A synthetic browser check after these changes reached playback 4.709 seconds after final transcription and passed forced worker replacement while keeping the microphone muted, with no browser errors.

For faster audible cutoff, an enabled, echo-cancelled microphone is also checked locally every 20 ms for 60 ms of sustained input energy. This is a provisional onset heuristic, not speech recognition or an emotion detector. It pauses/detaches browser playback while awaiting authoritative server VAD. It never sends a model request, enables a microphone, or records audio. Without confirmation, playback recovers after 1.2 seconds; at most one provisional cutoff is allowed per reply so persistent noise cannot repeatedly strand it. It is disabled while muted or paused. Noise can still cause a brief false cutoff, and quiet speech may rely on server VAD. In synthetic live tests, browser cutoff changed from 663 ms on the server-only path to 238–271 ms from test-audio start with local preemption. The final run verified fresh playback resumed and the counselor followed a spoken correction from 'manager' to 'brother', with no browser errors. These are development observations, not a sub-200 ms guarantee on real microphones/networks.

Voice-service health and browser transport are recovered separately. A failed service calls the authenticated `/voice/recover` endpoint inside the existing room; it does not disconnect the browser, obtain another join token, or republish its microphone. A delayed worker heartbeat is reported as `reconnecting` after 15 seconds and `disconnected` after 45 seconds without overwriting the worker's actual status, so a fresh heartbeat clears the warning. Dispatch checks health again after querying LiveKit and preserves a recovered worker. Even a token request marked `reconnect` cannot force a healthy worker to be replaced.

The SDK handles transport recovery first. Only an actually disconnected browser transport may create a new connection; application retries are bounded to three with backoff, and the retry budget resets only after a full minute of stable health. Service repair waits at least ten seconds, leaves microphone controls and typing available, and reports service recovery rather than claiming the browser call disconnected. Reconnection preserves a muted/paused microphone and never enables voice automatically after a page reload or permission denial.

Workers retry transient API failures up to three attempts with the same event identity; onset retries are deduplicated so a late acknowledgement cannot cancel a newer turn. Snapshot-read outages receive a bounded recovery window; authentication and superseded-lease failures are not retried. STT/TTS use bounded SDK retries. Voice failure logs contain only source/category metadata, not transcript content. Worker cleanup tolerates an already-closed AgentSession. `RoomOptions.close_on_disconnect=False` preserves the worker through a brief browser rejoin, following [LiveKit's session lifecycle guidance](https://docs.livekit.io/agents/logic/sessions/). An absent participant suppresses speech and has a 60-second rejoin grace period; an abandoned worker then closes so it cannot run indefinitely. Ending the conversation still closes it promptly. Real network or provider outages can interrupt audio; these controls prevent avoidable app-triggered disconnect loops, not all possible outages.

Connection regression checks on September 10: a 95-second, multi-turn synthetic voice session retained one worker and one browser join with zero disconnects while the browser received false failed-health reports for 25 seconds. A deliberate browser disconnect then rejoined that same worker with the microphone still muted. A separate synthetic provider failure replaced the worker while the existing browser transport remained connected, without another join token. These are local development tests, not a guarantee of uninterrupted operation under every network/provider condition. The reproducible live check is the ignored `app/web/.cache/check-voice-stability.mjs` (`--replace-worker` exercises a real, test-session-only service failure).

Explicit current first-person crisis disclosures take an immediate server safety path that works without a model call, including retries. Broader context can trigger the same overlay through a model control prefix, stripped before drafts, history, or speech. Partial prefixes and obsolete responses are fenced. If a provider fails after flagging a crisis, the server supplies the safety response. This is not a comprehensive or clinically validated crisis detector: the fast path covers a narrow set of English disclosures, and contextual recognition depends on the model. Clarifications and historical or negated statements are handled in conversation context. Crisis help remains manually available even without a session; dismissing it never claims the person is safe. Ending a session clears its crisis signal.

Resource links checked on September 10, 2026: [US 988 Lifeline](https://988lifeline.org/contact-us/), [Canada 9-8-8](https://www.canada.ca/en/public-health/services/mental-health-services/mental-health-get-help.html), [India Tele-MANAS](https://www.dghs.mohfw.gov.in/national-mental-health-programme.php), and [Find a Helpline](https://findahelpline.com/). The user chooses a region; the app does not infer their location. The panel distinguishes local emergency help from mental-health support and does not initiate calls or contact third parties automatically. Caption integration follows [LiveKit's text and transcription documentation](https://docs.livekit.io/agents/multimodality/text/).

The assistant identifies itself as AI support. It cannot connect to a human counselor or provide emergency help. Contextual responses to mental-health concerns are generated by the model, not a clinically validated assessment system. Use synthetic scenarios for evaluation.

## Verification

```powershell
cd app
.\.venv\Scripts\python.exe -m pytest -q
cd web
npm.cmd run build
npm.cmd run test:e2e
```

Backend tests cover conversation context, provider message formats and completion checks, duplicate inputs, interrupted history, cancellation-ignoring generation, paused/disconnected typed input, worker replacement, session ownership, error recovery, and transcript/note cleanup. Browser checks cover preferences reaching the API, reload, streaming drafts, quiet view, and session reset on desktop and mobile. Live provider observations are separate from deterministic tests.

## Evaluate before fine-tuning

`app/fixtures/counselor-conversations.json` contains thirteen synthetic scenarios and review criteria for the first meeting, specific reflection, corrections, rejected suggestions, continuity, direct requests, language, safety, meaning, and summaries. These are development evaluation cases, not a clinically reviewed training dataset. Review outputs yourself and add fresh holdout scenarios before drawing broader conclusions. See the [conversation design and sources](COUNSELOR_CONVERSATION_DESIGN.md) for how professional guidance informs these behaviors.

```powershell
cd app
# Inspect synthetic scenarios without calling a model:
.\.venv\Scripts\python.exe scripts/evaluate_conversation.py
# Generate paid provider replies, saved only in ignored .cache:
.\.venv\Scripts\python.exe scripts/evaluate_conversation.py --live
# Compare another accessible Vertex model without changing the running app:
.\.venv\Scripts\python.exe scripts/evaluate_conversation.py --live --model MODEL_ID --output .cache/comparison.json
```

The report includes response and first-text latency, plus criteria awaiting human review. It does not turn a successful API call into a quality score. Fine-tuning requires a model that supports it, a separately reviewed dataset of appropriate dialogue examples, and comparisons on held-out conversations. No training job is launched, and user transcripts are not collected for training by this app.
